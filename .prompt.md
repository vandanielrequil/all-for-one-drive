# Контекст проекта all-for-one-drive

## Цель

Go-приложение готовит фотографии и видео к резервному копированию, а затем
загружает их на несколько бесплатных хостингов согласно приоритетам.

## Архитектура

- `internal/` — изолированные, потенциально переиспользуемые модули.
- Команды:
  - `cmd/convert-and-upload` — конвертация изображений/видео, архивация, upload;
  - `cmd/convert` — только конвертация изображений/видео;
  - `cmd/precheck` — только PreCheck всех облаков в `availability.log`.
- `all-for-one.config.jsonc` — единый глобальный конфиг с комментариями.
- В JSONC комментарии всегда пишутся в конце той же строки после значения
  (`"key": value, // комментарий`), а не отдельной строкой выше ключа.
  Исключение — целиком закомментированные шаблоны провайдеров и короткие
  метки секций перед ними.
- По умолчанию конфиг ищется рядом с исполняемым файлом (`os.Executable()`).
- Пути в конфиге разрешаются относительно расположения файла конфига.
- Исходные медиафайлы неизменяемы: их нельзя перезаписывать или удалять.
- Не запускать никакие Git-команды, включая команды только для чтения.
- Не писать новые тесты, если пользователь явно этого не попросил.
- Логи: `internal/applog`, формат `модуль - функция - вход`.
- Лог пишется в консоль и в файл `{имя_бинарника}.log` рядом с exe;
  при каждом запуске лог очищается.
- Полная таблица доступности всех аккаунтов дописывается в
  `availability.log` рядом с exe (append; каждый PreCheck помечается
  меткой времени). PreCheck выполняется даже если файлов на загрузку нет.
- При ошибке создаётся `{имя_бинарника}.error` рядом с exe; при старте
  старый `.error` удаляется. Успешный прогон файл не создаёт.
- stdout/stderr внешних утилит rclone, ffmpeg, ffprobe и 7-Zip также
  дублируются в этот лог через `applog.Writer()`.

## Image converter

- Пакет: `internal/image-converter` (`package imageconverter`).
- Поддерживаемый вход: JPEG, PNG, GIF, TIFF и BMP; результат всегда JPEG.
- Сохраняется дерево поддиректорий и основа исходного имени файла.
- Существующий выходной файл пропускается, а не перезаписывается.
- При превышении `maxDimension` большая сторона уменьшается с Lanczos;
  маленькие изображения не увеличиваются.
- JPEG кодируется стандартным `image/jpeg` с параметром `quality`.
- Для исходных JPEG копируются валидные EXIF APP1-сегменты. Поврежденный EXIF
  не мешает сохранить обработанное изображение.
- Битый или неподдерживаемый файл не останавливает пакетную обработку.

## Video converter

- Пакет: `internal/video-converter` (`package videoconverter`).
- Требует `ffmpeg` в PATH.
- Поддерживаемый вход: MP4, MOV, AVI, MKV, WebM, M4V, WMV, FLV, MPEG, 3GP;
  результат всегда MP4 (H.264 + AAC).
- `maxDimension` — уменьшение только если сторона больше лимита; иначе размер не меняется.
- `quality` (1–100) маппится в libx264 CRF: `51 - quality*0.37` (83 → CRF 21).
- Метаданные копируются через `-map_metadata 0`.
- Исходники не трогаются; существующий выходной файл пропускается.

## Archiver

- Пакет: `internal/archiver`.
- `ArchiveDirectories` архивирует файлы по их относительной родительской
  папке: файлы из разных директорий никогда не смешиваются.
- Архивы пишутся в `archive-output/<relativeParent>/...7z`, поэтому rclone
  Upload зеркалит только пользовательские папки в `all-for-one/...`.
  Одинаковые относительные пути из image-output и video-output попадают в
  одну облачную директорию. Префиксов `images`/`videos` нет.
- Требует `7z`, `7zz` или `7za` в PATH.
- Формат: 7z без сжатия (`-mx=0`).
- Метод принимает опциональный пароль: пустая строка отключает шифрование,
  непустая включает `-mhe=on` и `-p...`.
- Группы ограничены `maxArchiveSizeMB`; архив проверяется после создания и при
  превышении пересобирается меньшими группами. Один файл больше лимита
  допускается как отдельный архив.
- Имя начинается с имени родительской директории и имени первого файла группы.
- Входная директория очищается только после успешного создания всех её архивов.
- Без архивации staging сохраняет относительные пути напрямую под
  `upload-output/...` без разделения на images/videos.

## Rclone

- Пакет: `internal/rclone`.
- Глобальный `replication` по умолчанию 3; глобальный `echelon` по умолчанию 1.
  Выбираются эшелоны от `echelon` до `min(3, echelon+replication-1)`, поэтому
  верхний эшелон ограничивает фактическое число реплик.
- Эшелонов жёстко три. Каждый провайдер имеет `echelon` 1–3 и `priority`
  0–101. Меньшее число priority загружается раньше внутри эшелона; `0`
  означает отключённый storage, `101` — заполненный. Оба всё равно проходят
  PreCheck и попадают в `availability.log`, но не выбираются для Upload.
- На каждый выбранный эшелон создаётся одна логическая копия набора без
  дублирования отдельных файлов. Файлы распределяются по целям в порядке
  возрастания priority:
  первая получает всё, что помещается в её доступную квоту, остаток переходит
  к следующей. Один файл внутри эшелона успешно загружается только в одну цель.
  Эшелон без доступных storage пропускается с предупреждением; ошибка только
  если ни один требуемый эшелон не доступен.
- `acceptsArchives` описывает возможность загружать архивы. При `archive: true`
  эшелон использует архивы, если хотя бы один его target принимает архивы;
  targets с `acceptsArchives: false` в таком эшелоне пропускаются. Если никто
  в эшелоне архивы не принимает — грузятся прямые файлы. Staging очищается
  только после успеха всех требуемых эшелонов.
- `maxUsageMB` — опциональный жёсткий потолок по размеру из `rclone size`.
  Если used уже >= лимита, PreCheck помечает аккаунт ошибкой; перед Upload
  проверяется used + размер пакета. Нужен для Cloudflare R2 (free 10 GiB),
  чтобы не уйти в платное превышение (обычно ставят 9900).
- `maxFileSizeMB` — опциональный лимит на один файл (Box free = 250). Файлы
  больше лимита не грузятся в этот storage и переходят к следующей цели
  эшелона. Upload отдаёт файлы rclone пачками (`rclone.batchSize`, дефолт 32)
  через `--files-from`; параллелизм внутри пачки — `rclone.transfers`
  (дефолт 4) плюс `--metadata`. Конвертеры и staging сохраняют mtime
  исходника для хронологии в облаке.
- Cloudflare R2 подключается только через rclone `type: s3` +
  `provider: Cloudflare` + `endpoint` вида
  `https://<AccountID>.r2.cloudflarestorage.com`. Нужны Access Key ID и
  Secret Access Key из R2 → Manage R2 API Tokens (не Account API Token).
- `options` — универсальная map с ключами из `rclone config providers`, поэтому
  модуль не привязан к конкретной версии или backend-у rclone.
- Для каждого аккаунта программа вызывает `rclone config create --obscure`;
  password-поля в JSONC задаются открытым текстом, а во временный config
  записываются уже obscured. Временный config имеет права `0600`.
- Значения секретов никогда не выводятся в лог.
- `PreCheck` проверяет аккаунты через `rclone about --json`, а для backend-ов
  без About (S3/Storj/R2) — через `rclone lsd`, затем `rclone size` показывает
  занятый объём. Если задан `maxUsageMB`, в таблице будет `used / limit`.
  Для Cloudinary корневой `lsd` не используется из-за ошибки backend-а на пустом
  `asset_folder`; вместо этого `rclone mkdir` создаёт `all-for-one` и
  одновременно проверяет авторизацию.
- Для Cloudinary PreCheck дополнительно вызывает Admin API `/usage` и выводит
  использованные/доступные кредиты и процент использования.
- `Upload` принимает `Target{Provider, Account}`, массив локальных путей и
  удалённую директорию.
- `PreCheck` всегда опрашивает все настроенные аккаунты независимо от echelon,
  priority 0/101 и пригодности для текущей репликации.
- `internal/oauth` выполняет первичную OAuth-авторизацию через rclone, хранит
  refresh token в отдельном файле и сохраняет обновлённый token при закрытии.
- `internal/twofactor` генерирует шестизначный RFC 6238 TOTP из Base32-секрета
  и записывает его в `twoFactor.outputFile`. Google Drive использует OAuth и
  не требует `twoFactor`; backend `drive` не принимает OTP-флаг.
- Если `twoFactor.rcloneOption` заполнен (например, `2fa` для MEGA), свежий код
  генерируется перед каждой rclone-командой и передаётся через backend-флаг.
- Верхнеуровневый флаг `archive` управляется оркестратором
  `cmd/convert-and-upload`: при `false` archiver не создаётся и обработанные
  медиафайлы загружаются напрямую.
- Архивация выполняется для целей с `acceptsArchives: true`; остальные цели
  получают прямые файлы из `rclone.uploadDir`. Относительные директории
  сохраняются без префиксов images/videos.
- После архивации содержимое `archive-output` загружается в директорию
  `all-for-one`; `Upload` предварительно вызывает `rclone mkdir`.
  `archive-output` очищается только после успешной загрузки.
- Cloudinary на текущем плане не принимает архивы; для него используется
  `acceptsArchives: false`.

## Запуск

- Сборка:
  - `go build -o ./bin/convert-and-upload.exe ./cmd/convert-and-upload`
  - `go build -o ./bin/convert.exe ./cmd/convert`
  - `go build -o ./bin/precheck.exe ./cmd/precheck`
- Конфиг: `./bin/all-for-one.config.jsonc` рядом с бинарником.
- Другой конфиг: `-config <путь>` у любой команды.

## Дальнейшая работа

- Конфиг со временем будет содержать credentials: перед их добавлением нужно
  вынести безопасный пример и исключить локальный конфиг с секретами из Git.
- Модули загрузки не должны зависеть от конкретной CLI-команды.
- Для повторных запусков предпочтительны идемпотентные операции.
- Не менять и не удалять пользовательские исходники даже при ошибках.
